# 端到端赛道：三人分工与对接方案

本方案面向三名具备 AI 基础、正在补充量化知识的队员。数据尚未发放时，可以完成接口设计、模拟输入和模块实现；字段、标签与评测口径在拿到官方数据及模板后确认。

## 1. 分工结论

按完整计算链划分责任：

```text
历史行情与盘口 -> A：数据管线、InputEncoder -> tokens
tokens       -> B：TemporalBackbone、Head -> scores
scores       -> C：损失、评估、平台推理 -> 实验结论与提交结果
                         B：训练引擎将三部分连接并联合优化
```

| 队员 | 主责 | 必须交付的工程工作 | 独立研究方向 |
| --- | --- | --- | --- |
| A：输入与表示 | 把合法历史数据变成可学习 token | 数据读取、样本窗口、缺失处理、标准化、采样器、可训练 encoder | 数值分组编码、盘口结构编码、分钟与 [patch](https://arxiv.org/abs/2211.14730)（分段编码）token |
| B：主干与训练 | 从 token 学到预测分数，完成联合训练 | 主干、预测头、训练循环、设备管理、早停、完整检查点 | [GRU](https://pytorch.org/docs/stable/generated/torch.nn.GRU.html)（门控循环单元）、[时序卷积](https://arxiv.org/abs/1803.01271)、[Transformer](https://arxiv.org/abs/1706.03762) 及[池化](https://pytorch.org/docs/stable/nn.html)方式 |
| C：目标与评测 | 判断分数是否改善比赛表现，完成平台推理入口 | 损失函数、本地指标、官方评估适配、推理 Notebook、提交清单 | 排序目标、稳定性、[换手](../README.md#33-换手与压力场景)与收益表现的权衡 |

这不是按“模型、杂务、提交”分工。三人分别拥有一个可研究的模块和一组必要工程任务。A 前期工作较多，B 在训练阶段较多，C 在评测和提交阶段较多；按整个项目衡量负担，并每周重新分配超量任务。

## 2. A：数据与 InputEncoder

### 工程责任

- 核对字段单位、分钟记录代表的时间区间、数据实际可见时间、交易时段、复权口径与历史股票池。
- 实现只读取必要字段的数据适配器，训练和推理调用同一套处理逻辑。
- 在合法决策时点构建历史窗口。明确午休、跨日、停牌和缺失分钟的处理；不能把午休补成真实成交。
- 标准化参数仅由训练区间拟合，保存后用于验证与推理。
- 输出观测掩码；真实零值和缺失零填充必须可区分。
- 提供同一决策时点的股票采样方式，供 C 的截面排序损失使用。
- 和 C 一起核对标签，A 实现标签数据构建及边界信息。

### 研究责任

首先实现原始数值与掩码的分组 MLP，比较价格、成交、盘口分别编码后融合的方案。再考虑学习式 patch 编码或盘口档位结构编码。必要的单位变换、价格尺度处理与标准化属于输入处理；大量人工因子应作为单独的对照实验，而非默认输入。

**交付完成的标志：** 可追溯的字段说明、可重复的窗口构建、训练与推理一致的处理器、满足共同接口的可训练 encoder。

## 3. B：TemporalBackbone、Head 与训练引擎

### 工程责任

- 将 A 的 encoder 和自己的主干、预测头装进同一个完整模型。
- 实现优化器、[学习率计划](https://pytorch.org/docs/stable/optim.html)（learning rate scheduler）、[梯度裁剪](https://pytorch.org/docs/stable/generated/torch.nn.utils.clip_grad_norm_.html)、设备转移、早停与恢复训练。
- 调用 C 提供的损失和评估入口，用统一验证结果选择检查点。
- 保存 encoder、主干、预测头的参数，以及预处理状态、字段顺序、配置、随机种子和数据切分标识。
- 实现模型加载与批量预测，供 C 的平台 Notebook 调用。
- 测量真实数据下的训练显存、推理内存和耗时，调整 batch 与股票分块。

### 研究责任

先以小 GRU 建立共同基线，再比较 patch Transformer 或时序卷积。默认采用逐股票时序模型，同一股票历史窗口输出一个分数。跨股票注意力、多频融合等改变输入轴的架构，需要三人共同更新接口和推理方案。

**交付完成的标志：** 一次完整训练可保存并恢复，加载后的模型能使用 A 的处理器预测，并由 C 的评估器形成报告。

## 4. C：Objective、Evaluation 与平台推理

### 工程责任

- 和 A 核对官方目标的 VWAP 窗口、端点、价格基准及跨午休规则，记录公式与出处。
- 实现 [Huber](https://pytorch.org/docs/stable/generated/torch.nn.HuberLoss.html) 基线损失、同一截面排序损失与可配置组合。
- 实现研究用 [IC](../README.md#31-ic-与-ic_ir)、[IC_IR](../README.md#31-ic-与-ic_ir)、多空收益、[夏普](../README.md#32-多空组合夏普)、压力分组与换手诊断，并记录样本数量及覆盖率。
- 核对官方去极值、标准化、[BARRA](https://www.msci.com/data-and-analytics/factor-investing/equity-factor-models) 风格剔除与最终评分口径，用官方评估结果校准本地报告。
- 实现唯一的推理 Notebook：通过 `datasources` 读取数据，调用 A 的处理器和 B 的模型加载入口，返回规定格式。
- 整理离线依赖、文件清单、运行日志与平台报错，组织提交演练。

### 研究责任

比较回归、截面排序及稳定性约束的收益。逐项说明其改善哪一个比赛指标。换手惩罚、可微组合损失需要先明确持仓构造、股票对齐和时间连续性，不能直接拿相邻 batch 的不同股票分数相减。

**交付完成的标志：** 同一模型有可追溯的研究报告和官方报告，线上可加载已训练权重完成合法推理。

## 5. 三人先约定的共同接口

以下为拟定的 v1 接口，属于下一阶段实现目标。当前原型不代表所有接口已实现。

### 5.1 样本批次：A 提供

| 字段 | 形状 / 类型 | 语义 |
| --- | --- | --- |
| `x` | float32 `[B,L,F]` | 标准化后的历史原始字段；缺失填零 |
| `observed` | bool `[B,L,F]` | True 表示实际观测到该字段 |
| `decision_id` | int64 `[B]` | 决策时点标识；同一时点跨股票完全相同 |
| `instrument` | 长度 B 的元数据 | 股票代码；默认不作为股票 ID embedding |
| `available_at` | 时间戳 `[B,L]` | 每条记录实际可用时间，用于未来数据检查 |
| `target` | float32 `[B]` | 仅训练与离线评估使用的未来收益标签 |
| `label_end_at` | 时间戳 `[B]` | 标签覆盖结束时间，用于切分边界检查 |

其中 B 为样本数，L 为历史分钟数，F 为真实字段数。候选起点为 L=120、隐藏维 D=64，先接 `bar1m`；这些是实验初值，不是比赛要求。时间升序排列，最新记录在右，左侧不足部分填充。具体哪些数据可见以官方时间语义为准。

无有效输入的样本由数据管线标记并按统一策略处理；不得悄悄删除造成整段缺失。元数据与张量始终保持相同顺序。

### 5.2 Token 接口：A 到 B

```python
tokens, token_valid = input_encoder(x, observed)
# tokens: float32 [B,N,D]
# token_valid: bool [B,N], True = 有效 token
```

A 负责 token 生成、分组、patch 划分、顺序与语义；B 负责[位置编码](https://arxiv.org/abs/1706.03762)、时序主干、池化和预测头。不要在两侧重复添加位置编码。分钟 token 的 N=L；patch 方案的 N 由 padding 和 patch 规则确定，规则必须写入配置。

所有外部接口统一 True=有效；调用 PyTorch 的 [padding mask](https://pytorch.org/docs/stable/generated/torch.nn.Transformer.html) 等 API 时，由模块内部转换成其要求的含义。全缺失窗口的处理要明确，避免全掩码注意力出现 NaN。

### 5.3 分数与损失：B 到 C

```python
scores = temporal_model(tokens, token_valid)  # [B]
loss = objective(scores, target, decision_id)
# 完整推理模型：model(x, observed) -> scores [B]
```

分数越大，预期未来收益越高。截面排序只能在同一个 `decision_id` 内计算；不同日期的样本不能直接组成排名对。模型 forward 不接收 `target` 或未来信息。损失可以使用训练标签，但推理输入完全由历史信息构成。

### 5.4 联合训练与检查点

A 的 encoder 是可训练模型的一部分，梯度必须回传到它，B 的优化器必须包含它的参数。可以缓存确定性的原始窗口或标准化数值；默认不缓存学习后 token，以免训练时冻结 encoder。

训练窗口可使用切分之前的历史上下文；训练标签不得覆盖验证区间。A 与 C 按 `label_end_at` 清除越界标签，B 使用三人共同冻结的时间切分。不得随机打散年份做训练/验证划分。

预处理状态和字段顺序随检查点保存。C 的推理入口直接调用共享代码，不能另写一套标准化、窗口或模型结构。

## 6. 文件责任与协作方式

当前 `model.py` 同时包含 encoder 与主干。下一阶段建议逐步拆分，以下新增文件名是规划，尚未全部实现：

| 队员 | 主要文件边界 |
| --- | --- |
| A | `contracts.py`、`preprocessing.py`，拟新增 `data_adapter.py`、`input_encoder.py` |
| B | `model.py`，拟新增 `backbones.py`、训练入口与检查点模块 |
| C | `losses.py`、`research_metrics.py`，拟新增官方评估适配与推理 Notebook |

- 每人使用独立 Git 分支，例如 `codex/input-encoder`、`codex/backbone-training`、`codex/objective-evaluation`。
- 共享接口、字段配置和实验切分的修改由三人确认；日常模块修改由负责人实施。
- 对接错误回到所属模块修复，C 不承担所有人的收尾修改。
- 交叉审阅：C 审 A 的时间与标签；A 审 B 的梯度及检查点；B 审 C 的指标与推理一致性。
- 每人同时推进一个必要工程任务和一个研究实验，完成后再启动下一个架构变化。

## 7. 保证最后能接上的工作节奏

### 数据发放前

1. 三人确定接口 v1、配置格式、环境版本和文件责任。
2. A 提供模拟 batch 与 encoder；B 接上最小主干；C 提供损失与报告格式。
3. 在统一 PyTorch 环境完成一次 forward、backward、保存和加载对接。当前本地原型尚未完成神经网络实际运行，这应成为首个共同里程碑。
4. 准备官方字段、标签和评测待确认清单。未知内容留作明确配置，不凭猜测写死。

### 数据到达 D0 至 D0+3

- D0：A 核对字段和时间，B 准备训练执行，C 核对官方标签与评估模板。
- D0+1：冻结最小真实数据 schema 与时间切分，三人接通一个短区间。
- D0+2 至 D0+3：完成第一版真实数据训练、保存、加载和评估；发现口径问题时先修口径。

### 后续研究与提交

每天一次小规模集成：使用当天三个人的模块跑共同短区间，记录版本、样本数量、覆盖率及报错。轮流负责组织对接，不把集成永久交给 C。

冻结共同基线后，每次主要改变一个因素，其他模块保持基线版本。记录切分、种子、检查点、各项指标、运行时间以及相对基线变化。用相同日期和股票覆盖范围比较，避免把缺失股票变化当作模型提升。

建议最迟 10 月 20 日获得一次平台有效运行，10 月 26 日完成候选提交演练。官方公榜截止为 10 月 29 日 23:59:59，私榜候选选择截止为 10 月 30 日 23:59:59。数据若晚到，减少高级架构实验，保留完整数据口径检查和平台演练时间。

## 8. 如何以比赛指标决定研究任务

| 研究问题 | 主要负责人 | 观察指标 | 必须联动的人 |
| --- | --- | --- | --- |
| 输入尺度与盘口结构是否更容易学习 | A | IC、IC_IR、压力场景稳定性 | B 确认主干条件一致，C 对齐报告 |
| 长历史与时序架构是否有效 | B | IC、IC_IR、多空夏普、推理耗时 | A 检查窗口，C 检查样本外表现 |
| 排序与稳定性目标是否改善交易信号 | C | IC、多空夏普、换手、压力表现 | B 接入训练，A 提供时点与股票对齐 |

说明中列出五类评价指标，但没有给出最终加权评分公式。研究版 RankIC、夏普和换手也不自动等于官方算法。C 必须核实官方实现；在此之前记录各项指标及其口径，避免宣称已直接优化官方总分。

## 9. 负担调整与最终验收

每周按剩余任务和阻塞情况调整，不以代码行数比较工作量。A 数据接通后承担输入消融和缺失诊断；B 长训练运行期间承担推理性能优化；C 等待平台结果期间承担损失消融和稳定性分析。无人因等待数据或训练而闲置，也无人承担全部集成工作。

最终共同验收：

- 真实输入可追溯，所有可用时间不晚于决策时点，标签口径得到确认。
- encoder、主干和预测头联合训练，检查点包含重现推理所需状态。
- 时间切分与标签边界合规，模型选择依据固定样本外评估。
- 输出满足平台最终合同，并按约定控制区间、合法采样点、缺失、重复和非法数值。
- 提交有且仅有一个 Notebook，依赖与参数完整，无需外网，可在三小时上限内完成。
- 每个人都能解释输入如何变成 token、token 如何变成 score，以及 score 如何被评估。

队伍各成员可以独立提交，最终有效成绩按官方团队规则取最高分；共同基线和实验记录仍应统一，以便复现最好的候选。
